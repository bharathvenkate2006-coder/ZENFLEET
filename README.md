# ZenFleet: Predictive Speed Modulation for Decentralized AMR Fleets

**Smart India Hackathon 2026 | Problem Statement SIH26123 | Bharat Electronics Limited**
**Author: BHARATH V**

## What this is

In our Zenoh-based fleet coordination design, robots share position and intent directly with
each other and there is no central server. This repository holds the small prediction model that
sits inside each robot and helps it decide how fast to approach a shared junction.

Instead of the usual stop-and-wait rule, where a robot halts completely and then accelerates
again, each robot works out when the other one will clear the junction and eases off just enough to
arrive right after. The aim is to save the time a full stop would cost. **The traffic simulation
in `traffic/` did not show that saving yet** (see "Where things stand" and
`traffic/docs/RESULTS.md`): the robots stop far less, but tasks do not finish sooner.

## What the model predicts

Given the state of two robots approaching the same junction, it predicts:

1. **Median clearing time (Q50):** when the other robot will most likely have cleared the junction.
2. **Cautious clearing time (Q90):** a safer estimate that is right about 90% of the time.
3. **Conflict probability:** how likely it is that both robots would be in the junction together.

These feed a speed command (`v_cmd`) and an action state: GO, SLOW, YIELD or STOP.

## Safety comes first

The model only **suggests** a speed. A rule-based safety layer has the final say, and it can only
lower the speed, never raise it:

- Blocked path: stop.
- Old peer data, lost heartbeat, or stale position fix: crawl speed.
- Junction lease not granted: the speed is capped so the robot can always stop before the junction.
- The command never exceeds the planned speed.

The design intent is that the lease and stopping-distance rules, not the ML model, keep the fleet
collision-free. In the traffic simulation there were 0 collisions in 390 runs, which is consistent
with that, but it is a simulation result: the lease there is an abstract arbiter.
The model's job is to make the fleet faster and smoother.

## When a robot can't finish its job (cnp/)

The `cnp/` folder handles task reassignment. Robots announce a stuck job, bid for it, and the winner
needs a majority of the fleet to approve before it starts, so two robots never own the same task.
The bids use the trained models here: a robot whose route runs into another robot at a junction bids
higher, using the Q50/Q90 clearing times and conflict probability, and a robot without enough range
declines. If the speed controller reports a fallback that does not clear, the robot hands its task
over. See [`cnp/README.md`](cnp/README.md) and [`cnp/docs/RESULTS.md`](cnp/docs/RESULTS.md).

## About the data (please read)

We did **not** train on data recorded from real robots. The training data is generated by
simulation, and this is what the dataset contains:

- Two robots approaching a junction with random speeds, distances, payloads (0 to 30 kg) and priorities.
- Peers that change speed and sometimes stall, so the ground truth is not perfectly predictable.
- Delayed and noisy peer messages, including occasional dropouts, and position error that grows
  when the last floor-marker fix is old.
- Labels measured directly from the simulated motion: the real time the peer cleared the junction,
  and whether the two robots' junction occupancy actually overlapped.

We chose simulation because collisions and near-misses are exactly the events you do not want to
collect from real robots, and because the problem statement itself calls for testing with
15 to 20 virtual robots alongside the 3-robot hardware demo.

**What this means for the results:** the numbers below show the model learns useful structure. They
are not a claim about performance on physical AMRs. The robot parameters (speed, mass, braking) are
assumptions we set in `src/generate_dataset.py`.

**Our plan for real data:** log the same columns from the 3-robot hardware run and from the
Gazebo/Isaac simulation, then retrain and recalibrate. The training code takes any CSV with the same
column names, so nothing else needs to change.

## Results

Tested on a junction layout the model never saw during training:

| What we measured | Result |
|---|---|
| Error in predicting peer clearing time, physics formula alone | 5.75 s |
| Same error with the model (Q50) | 3.39 s |
| How often the true time falls under the Q90 estimate | 89.2% (target ~90%) |
| Conflict detection, PR-AUC | 0.67 (base rate 24%) |
| Conflicts caught at our chosen threshold | 96% (with many false alarms, precision 41%) |

We also compared linear regression, Random Forest, ExtraTrees and LightGBM. Random Forest came within
0.03 s of LightGBM on clearing time; linear regression did well on timing but poorly on conflicts.
LightGBM was best overall, so we use it.

Two honest limits: the 3.4 s error is much higher than we would like, mostly because the simulated
peers stall at random and that cannot be predicted. And the high recall makes the robot cautious, so
the real test is whether the completion-time gain over stop-and-wait holds up when this runs in the
full simulation. We have not measured that yet.

## Try it

```bash
git clone https://github.com/bharathvenkate2006-coder/ZENFLEET.git
cd ZENFLEET

python -m venv .venv
# Windows:   .venv\Scripts\activate
# Linux/Mac: source .venv/bin/activate

pip install -r requirements.txt
python src/predict.py
```

You should see:

```text
TTC Q50 (median time peer clears):     5.0 s
TTC Q90 (cautious time peer clears):   8.23 s
Conflict probability:                  0.626  (threshold 0.13) -> CONFLICT
Speed command v_cmd:                   0.171 m/s  (alpha=0.171)
Action:                                YIELD
```

To try your own case, copy `examples/sample_input.json`, change the numbers, and run
`python src/predict.py my_input.json`.

## How the pieces fit

```text
15 inputs: speeds, distances, lease status, priority, payload, message age, ...
        |
 + 5 derived: stopping distance, physics arrival times, time gap
        |
        v
 Q50 model, Q90 model, conflict model
        |
        v
 speed suggestion  =  distance / (Q90 time + buffer)  x  (1 - risk)
        |
        v
 safety layer (overrides the model)
        |
        v
 v_cmd, alpha, action state, fallback flag
```

## Retraining

```bash
python src/generate_dataset.py --n 60000 --out amr_junction_dataset.csv
python src/train_model.py --data amr_junction_dataset.csv --out models
cp models/meta.json config/meta.json
```

The trained files were saved with LightGBM 4.7.0 and scikit-learn 1.8.0, which are pinned in
`requirements.txt`. If a different version fails to load them, just retrain.
